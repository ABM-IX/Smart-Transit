SmartTransit

A real-time, multi-modal intelligent transport system for Gaborone

Coordinating passenger information, vehicle spacing and connected journeys across paratransit.

A working software prototype combining Flutter mobile clients, a FastAPI real-time backend and a web operations dashboard. This presentation describes the system, its algorithms, current evidence and the work needed for field evaluation.

Context

A coordination problem across everyday transit

Demand-led services make it difficult to plan a trip from a phone screen alone

Limited arrival information

Without dependable live vehicle updates, passengers have little information about approaching services or likely waiting time.

Passenger need: clearer arrival and service information.
Vehicle spacing

Vehicles can cluster on a corridor, creating uneven service intervals and long gaps between arrivals.

Operator need: better visibility of spacing along shared routes.
Transfers between modes

A journey may combine a special cab, a combi and an intercity coach, each with separate service information and timing.

Planning need: make transfer options and assumptions visible.
Design implication · build for variable service, not fixed timetable assumptions

Research Aim

Coordinate information across paratransit modes

Design and implement a prototype ITS for passengers, drivers and service operators in Gaborone

Research question

How can a mobile and web-based system improve service visibility and coordination when transit operations are variable and demand-led?

Project objectives
  • Provide live vehicle and request information through mobile clients.
  • Apply spatial matching and proximity rules to selected workflows.
  • Generate corridor spacing advisories from vehicle locations.
  • Prototype multi-leg journey planning and operator monitoring.
  • Assess functional performance and identify what needs field evaluation.
Scope · prototype design, implementation and evaluation

System Design

Three interfaces, one connected service model

Mobile clients exchange trip and location events with the backend and operations dashboard

Passenger app · Flutter

Provides passenger-facing transit and trip workflows:

  • Vehicle locations and arrival estimates.
  • Taxi and combi hail requests.
  • Multi-modal itinerary planning prototype.
  • Trip and boarding events.
Driver app · Flutter

Supports driver status, trip and location workflows:

  • Location updates through the real-time connection.
  • Spacing advisory display for eligible vehicles.
  • Incoming hail and trip status updates.
  • Fare estimate display.
Operations dashboard · React

Provides fleet and service monitoring views:

  • Vehicle registry and current location views.
  • Route, stop and hail information when available.
  • Operational events and basic report views.
  • Data coverage depends on backend connectivity.
Backend · FastAPI · Socket.IO · Supabase

Core Algorithms

Location updates drive pacing advice and arrival estimates

The prototype translates GPS positions into simple distance-based rules

Spacing advisory rule
Gap to vehicle ahead < 200 m → SLOW DOWN
Gap > 800 m → SPEED UP
Otherwise → MAINTAIN SPEED

Haversine distance estimates the separation between reported positions. Advisories are intended to flag unusually close or wide gaps; they are guidance, not automated vehicle control.

Speed-floored ETA
ETA = distance ÷ max(current speed, 5 m/s)

The 5 m/s floor (18 km/h) prevents division by a near-zero speed from producing an unbounded estimate. This simplified estimate does not model traffic conditions or dwell time.

Current limitation: vehicle order is approximated from latitude; corridor direction and route geometry are needed for robust headway measurement.
Current implementation · proximity rules with explicit thresholds

Graph-based itinerary generation

The backend assembles candidate legs and calculates indicative departure and arrival times using configured travel durations and transfer buffers. These are prototype estimates, not live operator schedules.

Fare estimation

The itinerary sums leg fares using current project rules, including BWP 9 combi and BWP 10 standard taxi defaults. Coach fares and special-cab estimates depend on the configured data and assumptions.

Illustrative flow · transfer quality depends on route and timetable data

Operations dashboard · React

The dashboard provides searchable fleet views, vehicle details, route and stop data, hail queues, connection status and recent operational events.

Operational value

A shared desktop view can help an operator inspect fleet activity and identify records that need attention, while the mobile clients support passenger and driver workflows.

Current boundary

The current interface does not establish complete regulatory coverage: historical occupancy, verified corridor geometry and validated compliance exports are not yet available as a reliable reporting dataset.

Prototype dashboard · live values depend on connected backend data

Evaluation

Functional checks are in place; field outcomes remain to be measured

Separate software behaviour from transport impact when interpreting results

Implemented verification

Automated tests cover geographic distance calculations, headway advisory thresholds, journey planning and API behaviour. These checks support functional correctness for selected cases.

Software-level evidence
Performance measures

Project materials report an API response observation of 340 ms. Repeat measurements under stated device, network and server conditions and report sample size and latency distribution before treating it as a benchmark.

Repeatable benchmark needed
Field evaluation

Compare baseline and prototype-assisted trips on a partner corridor. Measure waiting time, headway variation, successful transfers, task completion and user feedback with a defined participant sample.

Not yet established by the prototype
No field trial results are claimed in this presentation
Slide 08 / 10
Discussion

An integrated prototype; operational impact is still an open question

The contribution is the coordination of passenger, driver and operator workflows for local service conditions

Technical contribution

The prototype brings real-time location, spatial distance, simple headway rules, taxi and combi workflows, and multi-leg itinerary generation into one system.

Practical relevance

The design treats paratransit as a variable service. It combines fixed-route corridor monitoring with on-demand taxi dispatch and passenger-facing information.

Limits on the conclusion

A working prototype and software tests show feasibility of selected functions. They do not prove reduced wait times, improved headways, user acceptance or deployment readiness.

Academic contribution · integrated local prototype and testable evaluation framework
Slide 09 / 10
Next Steps

The next phase is a supervised, partner-led field study

Seeking academic feedback, attachment opportunities and introductions to transport operators or deployment partners

Proposed work plan
  • 1. Refine the data model: validate route geometry, stop records and operator workflows with local partners.
  • 2. Improve the algorithms: use route direction and corridor distance for headway calculations; document ETA assumptions.
  • 3. Run a small field evaluation: collect baseline and prototype-assisted observations with participant consent.
  • 4. Report results responsibly: publish methods, sample limits, system metrics and observed user feedback.
Partner contribution
Access to expertise and operating context
Academic supervision, attachment mentorship, route or fleet data, and a suitable pilot setting would help move the prototype toward evidence-based evaluation.
Discussion

SmartTransit is a prototype for improving information and coordination in Gaborone transit. The next step is to establish whether its workflows are useful, safe and reliable in real operating conditions.
